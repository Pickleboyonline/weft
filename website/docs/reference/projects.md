# Projects and packages

Every weft project has the same layout, in the spirit of Rails. The compiler
sees the whole program, so where a file lives never changes what it means:
the layout is a convention, so every project is predictable for people,
agents and generators.

## Layout

```text
todo-lists/
  weft.toml          the project's name and dependencies
  data/              records and their tables, one record per file
  commands/          functions that write: what handlers call
  queries/           functions that only read: what views use
  ui/
    App.weft         the client's root component, and the layout around every page
    pages/           one component per URL
    components/      one component per file
    styles/          global CSS
  checks/            invariants: `Check` values
  jobs/              scheduled work
  endpoints/         HTTP entry points for other systems
  externs/           extern declarations, with their host code
  effects/           user-defined effects and their handlers
  deploy/            deployments other than local
  simulate/          simulations
  schema/            generated, checked in
```

Every folder except `data/`, `commands/`, `queries/` and `ui/` is optional.

## What each folder is for

These are conventions. `weft lint` warns when something seems to be in the
wrong place, such as a command in `queries/`, but the program means the same
either way.

| Folder | Top-level bindings there are usually… |
|---|---|
| `data/` | records, aliases, `Table`s |
| `commands/` | commands, and helpers they use |
| `queries/` | queries, and helpers they use |
| `checks/` | `Check`s |
| `jobs/` | `Job`s and the functions they run |
| `endpoints/` | `Endpoint`s and the functions they run |
| `externs/` | `Extern`s, each with its host code beside it |
| `effects/` | `effect`s and `handler`s |
| `deploy/` | `Deployment`s |
| `simulate/` | `Simulation`s |
| `ui/` | `component`s, one per file |

`expect` lines can go in any file.

## Names

- **One project, one namespace.** There are no `module` lines and no imports
  within a project: every top-level name is visible everywhere. Two top-level
  bindings with the same name are a compile error.
- **Files are named after what they hold:** `data/item.weft` holds
  `record Item`; `ui/components/ItemRow.weft` holds `component ItemRow`.
  Commands, queries and checks are grouped by the table they're mostly about:
  `commands/items.weft`.
- **Tables are plural** (`items`) and **records singular** (`Item`), but tables
  are always declared. weft never guesses an English plural.

## `weft.toml`

```toml
name = "todo-lists"

[dependencies]
ui_kit = { git = "https://example.com/ui-kit.git", version = "1.4" }
```

## Packages

A **package** is a weft project with no `deploy/`: components, functions,
records and effects for other projects to use.

- Dependencies are listed in `weft.toml`, each under a short name.
- A package's names are used through that name: `ui_kit.Button(label: "Save")`,
  `ui_kit.Icon.Check`. There's no import statement.
- A package can declare tables and externs. A project using it gets them,
  placed by its own deployments.
- Versions follow semantic versioning. The compiler checks that the commands
  a package exposes keep compatible signatures within a major version.

## The schema folder

`schema/` records each deployed version of every table: its fields and their
types. It's generated by `weft deploy`, checked in, and reviewed, like Rails'
`db/schema.rb`. The compiler compares the code with it to:

- generate migrations for changed tables;
- reject a change it can't migrate safely, such as a new field with no default;
- know what clients still running older code may send.

## Generators

Generators write ordinary code into the layout, which you then own and edit:

```bash
weft new todo-lists
weft generate resource Item title:Text done:Bool list:Id(TodoList)
weft generate component ItemRow
weft generate page lists/[id]
weft generate simulation flaky_wifi
```

`generate resource` writes the record and table, create, rename and delete
commands, a list query, a row and a form component, and a not-blank check.
